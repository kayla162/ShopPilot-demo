## 一、資料來源的限制

### 1. 價格、庫存、商品資料只有下載當下的快照

- **限制：** 蝦皮賣家中心只有「商品表現」報表可以選過去的期間下載；「價格與庫存」「商品基本資料」只能下載當下的狀態，無法補下載過去的版本（賣家確認）。
- **實例：** 分析上個月時，銷量是上個月的，但價格、庫存、標題用的是之後才下載的快照。當時缺貨、後來補貨的商品，在上個月的分析裡會顯示成有庫存。
- **目前的處理：** 側欄註明「價格庫存快照：（下載日期）（不是期間當時的庫存）」。
- **改善方向：** 每週下載一次價格與庫存報表，自己累積歷史快照；累積幾週後才能做庫存趨勢和補貨建議（依銷售速度估算可售天數）。

### 2. 已刪除商品的銷量無法分析

- **限制：** 商品表現報表會列出之後被刪除的商品，但名稱只寫「由於商品被刪除而無法獲取訊息」，也沒有價格，無法歸類或比較。
- **實例：** 其中一家店的報表裡有十幾個已刪除的商品，賣出的幾件就沒辦法算進分析，所以分析的總銷量比報表總數少一點；另一家店的已刪除商品則都沒有銷量。示範資料也放了幾個已刪除的商品，可以在總覽看到這段說明。
- **目前的處理：** 總覽顯示「另有 N 個已刪除的商品本期賣出 M 件，不列入分析」，AI 問答的資料表也帶這個數字；自動化測試檢查「分析的銷量＋已刪除商品的銷量＝報表總數」。

### 3. 每份報表是一整段期間的彙總

- **限制：** 商品表現報表是整段期間加總，沒有每日或每週的數字，看不到期間內的變化（例如活動前後）。
- **實例：** 兩個月的報表天數不同（一期整月、一期只到月中之後），兩期可以在側欄切換分開看，但系統還沒有「這個月比上個月」的比較。
- **改善方向：** 期間比較（用日均銷量比，消除天數不同的影響）；每週下載 7 天的報表，累積商品層級的週趨勢。

### 4. 賣場層級報表沒有用到

- **限制：** 範圍只做商品層級。賣場層級的報表（例如 `shop-stats`：流量來源、整體轉換）匯入時標示為「不在本次分析範圍」，不讀取內容。
- **改善方向：** 加入賣場層級的分析模組（流量來源、訂單履約、優惠券、營運健康）。

## 二、分析方法的限制

### 5. 多數商品銷量很少，統計檢定常常不顯著

- **限制：** 小賣場的銷量集中在少數商品，大部分商品一期只賣 0–1 件，統計檢定的樣本不夠。
- **實例：** 小賣場裡，一期有賣出的一般商品往往只占少數，銷量第 1 名就占了很大一部分。價格帶分析的結論常常是「各價格帶的轉換差異不顯著」。
- **目前的處理：** 規則式建議用統計把關（例如「0 訂單」要預期訂單 ≥ 3、z 值 ≥ 2 才判定），樣本不足的標成「觀察中」；比較對象少於 3 個時加註「僅供參考」。
- **改善方向：** 累積多期資料、合併期間分析。

### 6. 類別和相似商品靠文字規則

- **限制：** 類別依 `keywords.yaml` 的關鍵字順序比對標題；相似商品用標題的字元雙字詞（bigram）相似度，不理解語意。換品類就要重調設定。
- **實例：** 換到不同品類的賣場時，沿用原本的設定會有大部分商品落在「未分類」，要依實際標題重調關鍵字。調整過程中也會出現誤判，例如標題同時含有兩個類別關鍵字的商品被歸到排在前面的類別，要靠調整關鍵字順序修正。
- **目前的處理：** 每家店可以有自己的設定檔；保養品的設定已存成範例（`config/examples/skincare/`）；自動化測試檢查未分類 ≤ 10%。
- **改善方向：** 用文字嵌入（embedding）做語意相似度，或讓 AI 協助建議分類規則（仍由程式判斷）。

### 7. 建議是規則式，不代表因果

- **限制：** 「高點擊零成交」「點擊率偏低」等建議是依門檻和統計判斷出的「值得檢查」的訊號，不能證明改了就會變好。曝光影響因子也是相關性分析，不是實驗。
- **目前的處理：** 每條建議都附上程式算好的數據依據，讓賣家自己判斷。
- **改善方向：** 建議追蹤：記錄賣家採用了哪些建議，比較採用前後的成效。

## 三、外部競品的限制

### 8. 外部競品要人工填寫

- **限制：** 為了不違反蝦皮使用條款（而且有反爬蟲機制），系統不爬蝦皮網站；外部競品要賣家用範本手動填名稱、價格、已售出。
- **目前的處理：** 範本預填每個商品的搜尋關鍵字和蝦皮搜尋連結，並帶入已經填過的競品，每週只要更新已售出。
- **改善方向：** 蝦皮分潤計畫 Open API（已確認台灣有開放，需申請審核；資料表已預留 `affiliate_api` 來源）。

### 9. 競品「已售出」是累計數

- **限制：** 蝦皮搜尋結果的「已售出」是商品上架以來的累計銷量，不能直接和自家的期間銷量比。同期銷量要用前後兩次記錄的差距推算，而且：
  - 記錄日期是上傳範本的那一天，要涵蓋報表期間的頭尾（前後 3 天內）；
  - 大的數字顯示成約數（例如「1.2萬」的精確度只有 1,000 件、「10萬+」只是下限），差距不可信。
- **實例：** 剛開始填競品的賣場只有一次記錄，要等下一次記錄才能推算同期銷量。示範資料的外部競品有兩次記錄，可以看到推算結果。
- **目前的處理：** 約數、記錄日期對不上、只有一次記錄的競品，都列在「推算過程」表並說明原因，不算進平均；推算結果一律加註「是估計值」。

## 四、AI 文字解釋與問答的限制

> 設計原則：所有數字都由程式計算，AI 只負責把結果寫成白話；AI 不能用或出錯時，核心分析完全不受影響。

### 10. 數字檢查擋得住編造的數字，擋不住放錯位置的數字

- **限制：** AI 回覆裡的每個數字都要在輸入資料裡找得到（含四捨五入、比例 ×100、百分比單位），找不到就整段擋下不顯示。但如果數字在資料裡、只是放在錯的地方，就檢查不出來。
- **擋下來的實例：**
  - Qwen 0.5B 把「銷量多 N 件」寫成「高出 N%」→ 加上百分比單位檢查後擋下。
  - Qwen 1.5B 把一個個位數的點擊率乘以 10 寫成「佔比達幾十 %」→ 擋下。
- **擋不下來的實例：**
  - 問「本期最該先處理什麼」，AI 把某個商品的「加購件數」說成「售出件數」。
  - 問兩個商品各賣幾件，AI 都答成第三個商品的銷量。
  - 問「哪個類別賣最好」，AI 把單一商品的銷量當成類別總銷量，答錯類別。
- **正確率評估（本機 Qwen 2.5 1.5B，題目和標準答案由程式從資料算出；在兩家真實賣場測的，資料不公開）：**

  | 賣場 | 答對 | 答錯 | 資料有答案卻說沒有 | 被擋下 |
  |---|---|---|---|---|
  | 服飾店 | 23/25（92%） | 0 | 2 | 0 |
  | 保養品店 | 22/25（88%） | 3 | 0 | 0 |

  單一商品的價格、類別、店裡有沒有某類商品、資料沒有的事，全部答對；錯誤都出在「要在清單裡找到對的那一列」的題目。評分只檢查回答裡有沒有標準答案，不檢查其他句子，所以這是正確率的上限。把 `SHOPPILOT_DATA_DIR` 指到示範資料的複本（做法見 README「本機執行」）之後，也可以用 `python -m shoppilot.llm.qa_eval` 在示範資料上重跑。
- **在清單裡找錯列（2026-10-29 改善）：** 資料表原本只有排好序的清單，Qwen 1.5B 常把清單後段（離問題最近）的商品當成第一名：示範資料問「全店銷量最高的商品是哪個？」答成全店銷量清單的第 9 名（13 件，第 1 名是 28 件），問「洋裝類賣最好的是哪個商品？」答成全店清單裡的一件短褲。問「哪個類別賣最好？」則常答成銷量第 1 的商品屬於的類別；示範資料和真實賣場剛好是同一個類別，所以評估裡看不出來。
  - **怎麼選改法：** 為了不對評估的題目調整，另外做開發集：示範資料換 3 個亂數種子產生的賣場、真實賣場銷量排名較後的類別，加上換句話說的問法（「哪個商品賣最好？」「上衣類最暢銷的是哪一個？」）和「它的價格」題，共 37 題，不含評估的題目：

    | 資料表的寫法 | 開發集答對 |
    |---|---|
    | 原本 | 28/37 |
    | 每列加「第 N 名」，只留商品、類別、價格、銷量 | 27/37 |
    | 每列改成一行文字「第 1 名：商品（類別，價格，件數）」 | 29/37 |
    | 全店摘要加「銷量最高的類別」 | 27/37（賣最好的類別 1/3 → 3/3） |
    | 再在全店、問到的類別的銷量排行後面加「銷量最高的商品」 | 34/37（某類別賣最好 6/13 → 12/13） |
    | 同上，但全店排行不再寫一次（全店摘要已經寫了） | **35/37** |

    把問到的類別清單放到最前面、問類別時拿掉全店清單，都變差。保留最後一種：清單的列不變，答案直接寫在排行旁邊。全店排行不再寫一次，是因為銷量第 1 的商品在資料表出現太多次時，問「本期最該先處理的是什麼？」常答成它（示範資料把那件 T恤說成要補貨，評分只檢查有沒有提到正確商品，照樣算對）；改用嚴格評分（回答第一個提到的商品要是第一條建議的商品）檢查，拿掉之後回到原本的水準。開發集可以用 `python -m shoppilot.llm.qa_eval --dev` 重跑（真實賣場的 4 題不在裡面）。
  - **沒有銷量的期間：** 單日資料全店 0 件時，排行的第一名其實只是曝光最多的商品。一開始寫「本期沒有商品賣出」，問「這家店有賣外套嗎？」就變成回答資料沒有（「有賣」被當成問賣出）；用開發集賣場把銷量歸零（21 題，`--dev --no-sales`）比較幾種寫法，原本 8/21、「沒有（本期銷量都是 0）」16/21 且「有沒有賣某類」不變差，用這一種。
  - **評估（示範資料和一家真實賣場的兩個期間，93 題）：** 同一批回答用舊評分和新評分（見下）各算一次：

    | 資料 | 舊評分：修正前 → 後 | 新評分：修正前 → 後 |
    |---|---|---|
    | 示範資料 | 28/32 → 31/32 | 28/32 → 32/32 |
    | 真實賣場 9/1–9/28 | 29/32 → 31/32 | 29/32 → 31/32 |
    | 真實賣場 9/29（單日） | 18/29 → 19/29 | 19/29 → 22/29 |
    | 合計 | 75/93（81%）→ 81/93（87%） | 76/93（82%）→ 85/93（91%） |

    新評分下「銷量最高的商品」1/3 → 3/3、「某類別賣最好的商品」2/6 → 6/6、「它」指題目裡的商品 1/3 → 3/3、「最該先處理的事」2/3 → 3/3，其他題型都不變，沒有題目從答對變答錯；線上 demo 的範例問題回到 6 題。單日資料的「全店銷量最高的商品」等題，修正後回答「目前的資料沒有這項資訊」而不是「本期沒有賣出」，新評分算對。
- **銷量 0 被當成沒有資料（2026-10-30 改善）：** 商品分析裡只有 `sales_units: 0.0` 時，問「這個商品本期賣了幾件？」小模型常回答資料沒有；在有銷量的賣場問 0 銷量的商品，更會編出別的數字（「本期共售出了 12 個」），這些數字在資料表別處出現過，數字檢查擋不到。商品分析開頭改寫「本期銷量：0 件（本期沒有賣出）」：開發集（3 個開發集賣場和銷量歸零版本，30 題）10/30 → 26/30，評估 93 題 85 → 89，沒有題目變差；單日資料還有 3 題銷量 0 的商品回答資料沒有。
- **評分的三個修正（各自獨立 commit）：** 比對商品名稱時不看空白（示範資料的商品名稱有空格，AI 常拿掉空格寫）；本期沒有商品賣出時，問「賣最好」要回答沒有賣出（或資料沒有）才算對，原本的標準答案只是曝光最多的商品；標準答案是 0 時，「本期沒有賣出任何一件」這種沒有阿拉伯數字的說法也算對。
- **目前的處理：** 資料表用中文欄位、清單先排好序（改了以後，5 題測試從答出 1 題提升到 5 題）；全店摘要寫出銷量最高的商品和類別，問到的類別的銷量排行後面寫出這個類別銷量最高的商品；銷量 0 的商品在分析開頭寫明沒有賣出；畫面說明 AI 只看程式算好的資料。
- **改善方向：** 加上「數字和商品的對應檢查」（例如回覆提到某商品時，旁邊的銷量要等於那個商品的銷量）；換更大的模型。

### 11. 意思寫反、說錯對象、中文數字都檢查不到

- **限制：** 數字檢查只看阿拉伯數字，看不懂句子的意思。
- **實例：** 小模型曾把缺貨的商品寫成「庫存充足」、把同類平均說成自己的數字、寫出「第三季度」這種資料沒有的說法，也偶爾混入簡體字；「三個」這類中文數字不在檢查範圍內。
- **說錯對象的實例（2026-10-28，已修正）：** 問答的資料表原本不管問什麼，都把側欄選的商品的完整分析放在「問題提到的商品的完整分析」底下。示範資料的側欄預設是銷量第 1 的「街頭 蝴蝶結 羅紋 短款 素面 T恤」，問「本期最該先處理的是什麼？」，Qwen 1.5B 回答這件 T恤有缺貨問題，但第一條建議是「甜酷 收腰 緞面 貼身 短裙｜全部規格缺貨」。
- **修正與評估：** 改成問題用「這個商品」「這件」「它」這類說法時，才帶側欄選的商品。問答評估加上 `--sidebar`，每題都帶側欄預設選中的商品（和 Dashboard、線上 demo 一樣）；另外也測側欄選了一個不是任何全店題答案的商品。示範資料和一家真實賣場的兩個期間共 72 題，本機 Qwen 2.5 1.5B：

  | 側欄條件 | 修正前 | 修正後 | 回答提到側欄商品、但它不是答案 |
  |---|---|---|---|
  | 不帶側欄商品 | 59/72（82%） | 59/72（82%） | — |
  | 預設商品（銷量第 1） | 61/72（85%） | 59/72（82%） | 1 → 0 |
  | 其他商品 | 58/72（81%） | 59/72（82%） | 5 → 1 |

  - 修正後不管側欄選什麼，資料表都和不帶側欄時一模一樣，回答也逐字相同（greedy decoding）。「最該先處理的事」兩種側欄條件都從 1/3 變成 2/3，示範資料的這一題回到線上 demo 的範例問題。
  - **變差的地方：** 側欄是預設商品時少答對 2 題，都是「銷量最高的商品」：舊的資料表等於把銷量第 1 名的完整分析交給模型，所以剛好答對；拿掉以後回到不帶側欄時的結果。這是第 10 項「要在清單裡找到對的那一列」的問題，線上 demo 的範例問題因此少了「全店銷量最高的商品是哪個？」（第 10 項的改善之後回來了）。另外有 3 題答案不是側欄商品的題目，因為資料表內容變了而改變答案（2 題變差、1 題變好），是小模型對輸入很敏感。
- **補上漏掉的說法（2026-10-29）：** 只認「這個商品」「這件」「它」太窄：「這個賣得好嗎？」「那個商品的價格？」「他的價格有競爭力嗎？」（錯字）「這包賣幾件？」都不會帶側欄的商品；反過來「哪個類別賣最好？它的營收多少？」的「它」指的是類別，卻會帶。現在加上「這個／那個」「那款」「這頂／這包」等說法和「他」；「它」前面已經有「哪」「什麼」「類」或別的商品時就不算。問答評估每份資料加上 7 題：側欄選銷量第 2、3 名的商品後，用不同說法問價格、銷量、類別，以及側欄選第 2 名時問「全店銷量最高的商品是哪個？它的價格是多少？」。同樣三份資料：

  | 題目 | 修正前 | 修正後 |
  |---|---|---|
  | 原本就會帶側欄商品的說法（這個商品、這件、它），9 題 | 6/9 | 6/9（輸入相同） |
  | 新補上的說法（這個、那個商品、他），9 題 | 2/9 | 7/9 |
  | 「它」指題目裡的商品，3 題 | 1/3 | 1/3 |

  - 新補上的說法修正前答對的 2 題都沒用到側欄的商品（其中一題是銷量第 1 名剛好和側欄的商品同價）。修正後還錯的 2 題：一題類別答錯；單日資料沒有銷量，問賣了幾件回答「目前的資料沒有這項資訊」。
  - 「它」的 3 題答對數沒變，但修正前答錯的 2 題都把側欄的商品說成全店銷量最高；修正後答錯的 2 題是在銷量清單裡找錯列（第 10 項）。
  - **「這件本期賣了幾件？」：** 帶了側欄的商品，3 份資料也都答錯。當時懷疑是商品完整分析的欄位名稱是英文（銷量是 `sales_units`），換成中文欄位重跑：3 份資料 93 題修正前後都是 73 題答對，每個題型都沒變，這題照樣答錯（其中一份改成回答「本期最該先處理的事」第一條的商品）；同樣問銷量，「那個商品本期賣了幾件？」3 份資料答對 2 題。所以原因不是欄位名稱，而是模型沒把「這件」對到側欄的商品；中文欄位沒有變好，所以沒有保留。之後改成把側欄的商品放在資料表自己的標題底下（「使用者在側欄選的商品（問題裡的「這個」「這件」「它」指的就是這個商品）」），不再和問題直接提到的商品放在一起：這題 3 份資料從 0 題變成 2 題答對（剩下的是沒有銷量的單日資料，仍回答資料沒有），「問側欄選的商品」18 題從 13 題變成 15 題、沒有變差的，其他題目的資料表沒變；全部 93 題從 73 題變成 75 題答對。
  - 原本 72 題在三種側欄條件下的資料表都沒變，上表的結果不變；線上 demo 的範例問題也都沒有這些說法，快取照樣對得上。
- **評分也改嚴：** 「最該先處理的事」原本回答裡有問題名稱（例如「全部規格缺貨」）就算答對，但前幾條建議常常是同一個問題名稱，把側欄的商品說成「全部規格缺貨」也會算對；現在有商品的建議要答出商品。
- **目前的處理：** prompt 規定只能用資料裡的數字、不可推測原因、結論要和程式算的一致；只送 AI 需要解說的欄位，不送原始報表；問題問到「這個商品」時才帶側欄選的商品。
- **改善方向：** 檢查回覆提到的商品是不是資料表裡和問題相關的商品（例如問全店最該先處理的事，回覆的商品要在建議清單裡）。

### 12. 小模型常不照格式寫

- **限制：** prompt 規定「3 到 5 句、不要條列、不要 Markdown」，小模型常常不遵守。
- **實例：** 小規模的模型比較中，Qwen 0.5B 和 1.5B 都有不少回覆沒照格式寫。Qwen 1.5B 有一次寫成「1. 2. 3.」條列，條列編號「2」不在資料裡，一度讓整段被數字檢查擋下。
- **線上 demo 的範例回答（2026-10-30）：** 示範資料「本期最該先處理的是什麼？」的回答把前幾條建議的依據整段照抄成條列，寫到輸出上限 400 tokens，停在「因此需要優」，還混了簡體字（「问题」「依据」「建议做法」）；評分只看有沒有答出正確的商品，所以被選成線上 demo 的範例、放進快取。現在預先跑 AI 選範例時改用嚴格評分（第一個提到的商品要是第一條建議的商品），也不收有簡體字、或寫到輸出上限的回答。這一題因此不再當範例，線上 demo 的範例問題從 6 題變成 5 題；訪客自己打這題時，畫面說明線上 demo 只提供預先算好的答案。
- **目前的處理：** 數字檢查略過行首的條列編號；問答畫面顯示前拿掉粗體符號；線上 demo 的範例不收有簡體字、被截斷的回答。
- **改善方向：** 讓「最該先處理的事」寫得短一點（例如資料表只給前幾條建議的重點），範例才能放回來；簡體字目前只偵測常見的字，沒有轉換。

### 13. 用 CPU 跑本機模型很慢

- **實例：** Qwen 2.5 1.5B 用 CPU 每題 30–80 秒，第一次使用要先載入模型約 30 秒，模型下載約 3 GB。線上 demo 用的是免費 CPU 方案，範例問題已預先算好，自己問的問題要等 30–60 秒，多人同時使用會排隊。
- **目前的處理：** 只有按下「AI 分析」或送出問題時才呼叫；相同的輸入直接用快取，不再計算。
- **改善方向：** 安裝 CUDA 版 torch 用顯示卡、量化模型（4-bit／8-bit），或展示時改用 OpenAI。

### 14. 問答每題獨立

- **限制：** 每個問題單獨回答，不帶前面的對話（小模型帶上對話紀錄容易混淆，資料表也會變長）。追問時要把商品或類別再講一次。

## 五、系統與測試的限制

### 15. 只能在本機單人使用

- **限制：** Dashboard 只開放 localhost，沒有帳號與權限；這是刻意的設計，因為報表含營業資料，也可能用到 API Key。線上 demo 是另外的唯讀示範模式（`SHOPPILOT_DEMO=1`），只放虛構資料，不能上傳報表。
- **改善方向：** 對外使用真實資料時可以用 Cloudflare Tunnel 加登入保護；多人使用要改成網頁後端（例如 FastAPI）加帳號權限，重用 `shoppilot/` 分析核心。

### 16. 真實資料測試不在公開版

- **限制：** 私人版有一組真實資料測試，用每家店每個期間的真實報表檢查匯入、加總、未分類比例、每個商品的分析、建議依據、AI 資料表大小，以及 Dashboard 實際切到該期間後各分頁都沒有錯誤。這些測試綁定真實資料，不放進公開版。
- **目前的處理：** 公開版的測試改用虛構的示範資料（`shoppilot/demo/`）檢查同樣的流程；需要真實報表的測試不放進公開版，公開版的測試全部執行、沒有略過。
- **其他：** 開發與測試環境是 Windows；修改程式後，Dashboard 要整個重新啟動才保證生效。
