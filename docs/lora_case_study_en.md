# Teaching a 1.5B Model to Use Tools: A LoRA Case Study for a Seller Q&A System

> ShopPilot is an analytics tool I built for my own Shopee shops. This write-up covers how its Q&A feature went from 59% to 96%: choosing the approach, generating training data, making the comparison fair, and picking between three training-data versions.
> Code: [ShopPilot-demo](https://github.com/kayla162/ShopPilot-demo) · Model: [Hugging Face](https://huggingface.co/kayla162/shoppilot-qwen2.5-1.5b-tools-lora) · [中文版](lora_case_study.md)

## 1. The problem: sellers ask about numbers in plain language

Typical questions are "How many of this item sold this period?", "Which pants sell best?", "What should I fix first?". The answers are in the seller-center reports, spread across several Excel files.

Three constraints shaped the design:

- **Numbers must be right.** Sellers restock and reprice based on them. Every number is computed by code; the model only phrases results. A numeric-grounding guard blocks any answer containing a number that isn't in the data.
- **It must run on an ordinary laptop.** Shop data shouldn't leave the machine, and the online demo runs on a free CPU host. So: Qwen2.5-1.5B-Instruct, 4-bit quantized, served by llama.cpp on CPU.
- **The data is structured numbers, not documents.** So no RAG over text chunks. The model calls tools; the tools run in code and return exact numbers.

## 2. Starting point: data table 89%, tool calling 59%

**Data-table mode** sends a ~5,000-character shop table with every question (shop summary, categories, top sellers, products named in the question). The model looks up the answer.

**Tool-calling mode** gives the model 7 tools: shop summary, category ranking, sales ranking, get product, search products, sidebar-selected product, and top to-do. The model decides what to query and only sees the slice it asked for.

The benchmark has 141 questions: 32 templated questions plus 15 long-tail product questions for each of 3 shops (a demo shop and two real shops). Questions and gold answers are computed from the same data, so grading is automatic and reruns on any shop or period.

| Mode (Q4, CPU) | 141 questions |
|---|---|
| Data table | 125 (89%) |
| Tool calling | 83 (59%) |

The tool-calling errors were concentrated. Classifying them one by one from `details.csv`:

- **Wrong tool.** "How many sold this period?" queried the sales ranking instead of the product.
- **Ignoring the sidebar.** The seller selects a product in the sidebar and asks "how many of *this* sold?". The model didn't map "this" to the sidebar-product tool: 0/18.
- **Saying "no data" after getting data.** The tool returned the number; the answer said the data didn't have it.

These are tool-use failures, not language or arithmetic failures, which is exactly what fine-tuning is good at.

## 3. Training data: generated by the evaluation code, no manual labeling

The evaluation already computes gold answers from data. One step further, the same code produces full demonstrations:

> question → correct tool call → actual tool output → gold answer written only from that output

- 13 question types, each with several phrasings; v1 has 662 examples.
- Every gold answer must pass the numeric guard before it's kept.
- **No training on the test.** Training shops use separate random seeds that don't overlap with the dev set, the evaluation demo shop, or the real shops; no evaluation, dev, or hand-written question appears in training (enforced by tests).
- Every question type must actually produce examples, also enforced by a test. That test exists because of a real bug: after a tool's output format changed, the "top to-do" generator read a stale field and that type silently vanished for several versions.

## 4. QLoRA on a 6 GB laptop GPU

- Base weights in 4-bit NF4; LoRA (rank 16, alpha 32, on q/k/v/o/gate/up/down) trained in bfloat16: 18.46M trainable parameters (~1.2%).
- Loss on assistant answers only; vocabulary logits computed only at loss positions; gradient checkpointing.
- RTX 3060 Laptop (6 GB): 1 epoch in 43.7 minutes, 2.1 GB peak GPU memory; validation loss 0.52 → 0.004.

## 5. A fair comparison: same precision, only the LoRA differs

The first comparison had a flaw: the fine-tuned model ran in transformers (bfloat16) while the base model ran in llama.cpp (4-bit), so part of the gap could come from precision.

So I wrote `scripts/export_lora_gguf.py`. It reads the safetensors directly and writes a GGUF adapter using llama.cpp's tensor naming, which loads on top of Qwen's official Q4_K_M model. Both sides then use the same 4-bit model, the same prompt, and the same CPU; only the LoRA differs.

| 141 questions | Base | Fine-tuned |
|---|---|---|
| Total | 83 (59%) | **135 (96%)** |
| Sidebar-selected product | 0/18 | **18/18** |
| Product units sold | 3/15 | **15/15** |
| Long-tail units sold | 0/15 | **15/15** |
| Top to-do | 1/3 | **3/3** |

- Both models answer the same questions, so I used an exact McNemar test: p < 1e-11.
- Training used only synthetic demo clothing shops. The two real shops (clothing, skincare) were never seen and still scored 98% and 91%.
- Of 141 questions, only 1 was answered wrong; the other 5 misses said "no data".

## 6. Three data versions, chosen by failure mode

v1 still missed some question types, so error analysis drove two more versions:

| Training data | Added | 141 questions | Wrong answers (excluding "no data") |
|---|---|---|---|
| **v1 (released)** | One question, one tool per type | **135** | **1** |
| v2 | Two-part questions; long "[Brand] item item" names | 126 | 2 |
| v3 | Casual phrasing, partial names, pronoun sidebar questions, top-N and category totals | 135 | 6 |

**v2 learned the new type and regressed on an old one.** "What's the best seller? What's its price?" went from 0/3 to 3/3, but sidebar questions fell from 18/18 to 6/18.

The cause was in the data. In two-part questions, "it" refers to the product from the first half. The model learned "it = the product mentioned earlier" and stopped checking the sidebar even when "it / this item" stood alone. Instead it searched for a product literally named "this item".

**v3 added the conflicting cases.** With standalone pronoun sidebar examples, both types were answered correctly (18/18 and 3/3), and the total matched v1 at 135.

**But it failed differently.** All 6 of v3's errors were confidently wrong unit counts, such as reporting 28 units as "3.88 units". Those numbers appear somewhere in the tool output, so the guard can't catch them. When v1 isn't sure, it says "no data".

For a seller, a wrong number is far more dangerous than "I don't know", so v1 is the release. v2 and v3 are reproducible with `scripts/train_lora.py --data-version 2|3`.

## 7. Evaluation design: keep dev and test separate

v2 and v3 were built after looking at errors on the 141 questions and hand-written set A, so those sets are no longer unseen for them. Two safeguards:

- **Hand-written sets A and B.** Each has 30 casual, seller-style questions on the demo shop, with gold answers still computed from data. A was used for error analysis and became a dev set. B was written before any v3 result, run once at the end, and never used to choose changes.
- **A larger-model reference.** Qwen3 8B on local Ollama, through an OpenAI-compatible API with thinking disabled, using the same tools and prompt.

| System | 141 questions (95% CI) | Set B |
|---|---|---|
| Data table · 1.5B | 125 (89%, 82–93%) | 20/30 |
| Tool calling · 1.5B | 83 (59%, 51–67%) | 16/30 |
| **Tool calling · 1.5B + LoRA v1** | **135 (96%, 91–98%)** | **21/30** |
| Tool calling · Qwen3 8B | 133 (94%, 89–97%) | 25/30 |

**Reading the numbers:**

- On 141 questions, the base → fine-tuned gain is certain (p < 1e-11), and the fine-tuned 1.5B matches a 5× larger Qwen3 8B.
- Data table vs. tools + LoRA differs by 7 points (p = 0.052), borderline. Both modes are kept and switchable in config.
- Set B has only 30 questions and wide intervals: the 1.5B variants don't differ significantly from each other or from Qwen3 8B (p = 0.22). It's better for finding which phrasings fail than for ranking.

Accuracies carry Wilson intervals; paired comparisons use exact McNemar tests and a paired bootstrap (`python -m shoppilot.llm.eval_stats`).

## 8. Next: real seller questions

So far every question was generated by code or hand-written in a seller's voice. The next step is real usage:

- Every Q&A turn logs the question, the answer, and the data period, and the seller can rate it 👍/👎. The monitoring tab shows the seller-judged accuracy per model and mode.
- `python -m shoppilot.llm.real_eval export` turns the log into a question file. Once gold answers are added (in the same format as the hand-written sets, computed from data), `python -m shoppilot.llm.qa_eval --real` reruns those real questions on any model or mode.
- The log stays in the shop's own database. It is not version-controlled and never exported to the public repo.

## 9. Takeaways

1. **Classify errors before deciding to fine-tune.** Nearly all of the 59% baseline's errors were tool-use errors, which synthetic demonstrations can teach without a bigger model.
2. **The evaluator is the best data generator.** If code can compute the gold answer, it can generate the demonstration, and training and evaluation can't drift apart.
3. **Control precision in comparisons.** Converting the LoRA to GGUF and applying it to the same quantized model isolates the effect of fine-tuning.
4. **New data can conflict with old data.** v2's "it" broke sidebar questions. Check per-type scores after every data change, not just the total.
5. **When totals tie, compare failure modes.** v1 and v3 both scored 135, but one says "I don't know" and the other states wrong numbers. Choose the version whose errors hurt users less.
6. **Be honest with small samples.** Gaps on 30 questions are often not significant; confidence intervals and tests are more convincing than bare accuracy.
